## 1. EXECUTIVE SUMMARY

The current component-integrity rule (GF + RF = GT within 0.01 AED/sqft) is **semantically incorrect**. The Mollak API uses the formula:

### **grandTotal = totalGF + totalRF − income**

Where `income` is a field in the `gfData` object of the Mollak API that represents **income generated by the jointly owned property** (e.g., common area rental income, advertising revenue) that **offsets** the service charges payable by owners.

**This `income` field was never captured in our CSV dataset.** Its absence caused 134 of 266 residential projects (50.4%) to be incorrectly flagged as "component mismatch."

The formula was verified on **45 projects with 100% match rate** (37 random + 8 key projects).

**Conclusion: GRAND_TOTAL_IS_AUTHORITATIVE** — `grand_total_aed_sqft` is the officially approved net service charge rate that owners actually pay, after deducting income generated by the property.

## 2. THE DISCOVERY

### 2a. Raw API Response Structure

The Mollak API (`https://gateway.dubailand.gov.ae/servicecharges/map`) returns:

```json
{
  "gfData": {
    "totalGF": 15.61,
    "grandTotal": 16.82,
    "income": 0.07,
    "charges": [
      {"categoryName": "Services", "cost": 1.95},
      {"categoryName": "Maintenance", "cost": 2.75},
      ...
    ]
  },
  "rfData": {
    "totalRF": 1.28,
    "charges": [{"categoryName": "Reserved Fund", "cost": 1.28}]
  }
}
```

### 2b. The Missing Field

Our fetch script (`fetch_service_charges.py`) captures:
- `totalGF` → `total_gf_aed_sqft`
- `totalRF` → `total_rf_aed_sqft`
- `grandTotal` → `grand_total_aed_sqft`
- `charges` → `charge_categories`
- `additionalChargesData.totalAdditionalCharges` → `additional_charges_total`

**It does NOT capture `gfData.income`** — the income offset field.

### 2c. The Formula

For Harbour Views 2026:
- GF = 15.61, RF = 1.28, GT = 16.82, income = 0.07
- GF + RF = 16.89 (old "expected" total)
- GF + RF − income = 16.82 = GT ✅

The "component mismatch" of 0.07 is **exactly equal to the income field** (0.07).

## 8. CATEGORY-LEVEL RECONCILIATION

For ALL tested projects:
- **Category sum** (Services + Maintenance + Utilities + Management + Insurance + Master Community + Improvement) = **totalGF** (General Fund)
- **Reserve Fund (RF)** is separate from categories
- **GT ≠ category_sum + RF** (when income > 0)
- **GT = category_sum + RF − income** (always)

## 10. AUTHORITATIVE FIELD CONCLUSION

### **GRAND_TOTAL_IS_AUTHORITATIVE**

**Evidence basis:**
1. The Mollak API provides `grandTotal` as a precomputed field inside `gfData` — it is NOT computed by our code
2. The formula `GT = GF + RF − income` matches 100% of 45 tested projects
3. `grandTotal` represents the **net service charge rate** that owners actually pay, after deducting property income
4. The mismatch rate increases over time (0% → 56.5%), correlating with more projects reporting income
5. The frozen 6 pass because they have income = 0 (no income-generating common areas)
6. The `income` field is an official Mollak API field, not a derived value

**The current component-integrity rule (GF+RF=GT within 0.01) is semantically incorrect.** It incorrectly flags projects with income > 0 as "component mismatch" when in fact the components reconcile perfectly once the income offset is included.
