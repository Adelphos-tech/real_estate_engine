# SHADOW FALLBACK BENCHMARK ENGINE — COMPLETE IMPLEMENTATION REPORT

**Date:** 2026-08-12
**Scope:** Backend-only shadow fallback benchmark engine for properties with insufficient exact-project DLD evidence.
**Status:** Complete, audited, backtested, awaiting production-integration approval.

---

## Section A: Executive Summary

A backend-only shadow fallback engine has been implemented to calculate comparable-sales benchmarks for MASTER properties that lack sufficient exact-project DLD evidence. The engine operates in **SHADOW MODE** — it does NOT modify production investment decisions, canonical signals, frontend displays, or data stores. It is exposed via a single debug endpoint only.

Key results:
- **2,154 / 2,614 properties** (82.4%) are eligible for fallback benchmarks.
- **56 verified area mappings** connect MASTER area names to DLD transaction areas.
- Backtest vs exact-project evidence: **34% median absolute error**, **55% mean absolute error**.
- All calculations use **real DLD transactions only** — no synthetic or estimated data.

| Level | Name | Trigger | Method |
|-------|------|---------|--------|
| 1 | EXACT_PROJECT_SAME_BEDROOM_EVIDENCE | Exact project match, same bedroom, sufficient transactions | Canonical — not fallback |
| 2 | EXACT_PROJECT_STATUS_BROADENED_EVIDENCE | Exact project match, same bedroom, status broadened | Median price of same-project, same-bedroom, any status |
| 3 | AREA_SAME_BEDROOM_SIZE_ADJUSTED_EVIDENCE | No exact project; area mapped; same bedroom; size known | Median PPSF × subject size (sqft), with size band ±25% |
| 4 | AREA_SAME_BEDROOM_EVIDENCE | No exact project; area mapped; same bedroom; size unknown | Median PPSF × subject size (if known) or raw median PPSF |
| 5 | NO_FALLBACK | No verified area mapping, ambiguous bedroom (<1), or insufficient transactions | Fallback not available |

## Section D: Verified Area Mapping Methodology

**How mappings were built:**
- For every MASTER property with exact-project DLD evidence, extract its `area` field and the DLD `AREA_EN` of its matched transactions.
- Aggregate by MASTER area → DLD area, counting unique supporting projects.
- **High confidence:** ≥10 supporting projects.
- **Medium confidence:** 3–9 supporting projects.
- **Low confidence:** 1–2 supporting projects.

## Section E: Size Unit Detection & Conversion (Critical Data Quality Fix)

**Problem discovered:** DLD `ACTUAL_AREA` field uses **mixed units** — some values are in sqft, others in sqm. This caused wildly incorrect PPSF calculations (e.g., PPSF of 15,000 instead of 1,500).

**Heuristic implemented:** `_detect_size_unit_and_convert(raw_size, bedrooms)`
- If `raw_size < 300` → treat as sqm, convert to sqft (`× 10.764`).
- If `raw_size < bedroom-appropriate threshold` (e.g., studio < 500, 1BR < 650, 2BR < 900) → treat as sqm.
- Otherwise → treat as sqft.
- **Impact:** 93 of 93 transactions in Jebel Ali test required conversion. Without this fix, backtest errors exceeded 1000%.

## Section F: PPSF Outlier Removal

- **Method:** IQR-based outlier removal on PPSF values.
- **Multiplier:** 1.5 (configurable).
- **Process:**
  1. Calculate PPSF for each transaction (`price / size_sqft`).
  2. Compute Q1, Q3, and IQR of PPSF distribution.
  3. Exclude transactions where PPSF < (Q1 − 1.5×IQR) or PPSF > (Q3 + 1.5×IQR).
- **Result:** Typically removes 1–5% of extreme outliers per area cohort.

## Section G: Fallback Calculation Steps

For a given property:
1. Load MASTER row.
2. **Level 1/2:** Check exact-project DLD evidence (same bedroom, then status-broadened). If sufficient, use canonical evidence.
3. **Level 3/4:** Look up verified area mapping. Query DLD transactions in mapped area with same bedroom count.
4. Apply size-band filter (if subject size known): `subject_size × (1 ± size_band_pct)`.
5. Detect and convert sqm → sqft for all transaction sizes.
6. Calculate PPSF for each transaction.
7. Apply IQR outlier removal.
8. Validate minimum transactions (default: 8).
9. Validate maximum project concentration (default: 60% from single project).
10. Calculate median PPSF, mean PPSF, P25, P75, IQR, MAD.
11. Multiply median PPSF × subject size = estimated benchmark AED.
12. Calculate APIL and Conventional % advantages vs subject price.
13. Assign confidence score based on transaction count, project diversity, area mapping confidence, and size adjustment.

## Section I: Backtest Methodology

**Goal:** Validate how well area-level fallback benchmarks predict exact-project benchmarks.

**Process:**
1. Identify all MASTER properties with exact-project DLD evidence (Level 1).
2. For each property, **hide** its exact-project transactions from the fallback engine.
3. Force the fallback engine to use area-level comparables only (Level 3/4).
4. Calculate the area fallback benchmark.
5. Compare fallback benchmark vs exact-project median.
6. Compute absolute % error: `|fallback − exact| / exact × 100`.

**Result:** 1,057 properties backtested.

### Interpretation
- **34% median error** means area-level fallback is directionally useful but not precise enough for standalone investment decisions.
- **P90 of 125%** means 10% of fallbacks are wildly off — these are properties in areas with heterogeneous pricing (e.g., mixed villa/apartment, mixed luxury/affordable).
- **Worst case (891%)** is typically a property in an area with very few transactions, or where the subject is a luxury unit but the area fallback includes mostly affordable units.

## Section K: Confidence Scoring

Fallback confidence is computed from:

| Factor | Weight | Description |
|--------|--------|-------------|
| Transaction count | 30% | ≥50 = full points, <8 = ineligible |
| Project diversity | 25% | ≥5 unique projects = full points |
| Area mapping confidence | 20% | high=1.0, medium=0.7, low=0.4 |
| Size adjustment applied | 15% | Size band = more precise |
| Outlier stability | 10% | Low MAD = stable PPSF |

**Confidence labels:**
- ≥80: **high**
- 50–79: **medium**
- <50: **low**

## Section L: Shadow Mode Safeguards

Multiple safeguards prevent accidental production integration:

1. **Debug endpoint only:** `GET /debug/fallback-benchmark/{property_id}` — not exposed in frontend.
2. **`production_eligible: false`** in every response — explicit flag.
3. **No canonical signal modification:** Fallback results are NOT written to `price_analysis`, `investment_decision`, or `objective_signal`.
4. **No data store writes:** Does NOT modify Qdrant, MASTER_FINAL.xlsx, or raw DLD CSVs.
5. **No frontend changes:** No UI components reference fallback data.
6. **Separate audit files:** Results live in `FALLBACK_DLD_*.xlsx` and `.md`, not in production data.

## Section O: Known Limitations & Risks

1. **34% median error is too high for standalone decisions.** Fallback should only augment, not replace, exact-project evidence.
2. **Area mapping is incomplete.** 275 properties (10.5%) have no verified area mapping.
3. **Studio/0BR/loft excluded.** 54 properties with ambiguous bedroom counts are not eligible.
4. **Size unit detection is heuristic.** ~2% edge cases may still be misclassified.
5. **PPSF assumes homogeneous quality within area.** Luxury vs affordable units in same area skew results.
6. **No time decay weighting.** Older transactions are treated equally to recent ones.
7. **No rental yield integrated.** Per user specification, rental yield is NOT part of this engine.

## Section U: What Is NOT in Scope (Explicitly Excluded)

Per user specification, the following are **deliberately NOT implemented**:

1. ❌ **Rental yield integration** — Fallback engine does NOT calculate or use rental yield.
2. ❌ **Frontend UI changes** — No display of fallback data to users.
3. ❌ **Production decision modification** — `investment_decision` and `confidence` are NOT altered.
4. ❌ **MASTER_FINAL.xlsx modification** — Master file is read-only.
5. ❌ **Qdrant modification** — Vector store is untouched.
6. ❌ **Raw DLD CSV modification** — Source data is immutable.
7. ❌ **Automatic reclassification** — INSUFFICIENT_EVIDENCE properties are NOT auto-changed to OPPORTUNITY/AVOID.
